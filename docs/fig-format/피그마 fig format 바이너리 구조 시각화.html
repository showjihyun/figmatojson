1. 한눈에 보기1. At a glance

.fig 파일은 5 레이어 디코드를 거쳐야 의미가 나온다. 가장 바깥은 표준 ZIP, 그 안의 canvas.fig 가 Figma 의 진짜 바이너리 (fig-kiwi). 이 archive 안엔 두 개의 압축 chunk — schema (568 type 정의) 와 data (35,660 노드의 평탄 message). data chunk 의 평탄 array 를 parent GUID 로 link 하면 우리가 보는 layer tree.

Decoding a .fig file takes five layers. The outermost is a standard ZIP. Inside, canvas.fig is Figma's actual binary (fig-kiwi format). The archive holds two compressed chunks — a schema (568 type definitions) and the data (a flat message of 35,660 nodes). Linking the flat array by parent GUID yields the layer tree everyone sees.

2. Layer 1 — 컨테이너2. Layer 1 — Container

2.1 ZIP wrapper

현대 Figma export 는 STORE 모드 ZIP (압축 없음). 첫 4 byte 가 50 4B 03 04 (ZIP magic) 이면 ZIP, 66 69 67 2D 6B 69 77 69 ("fig-kiwi") 이면 raw archive. src/container.ts:loadContainer 가 자동 분기.

Modern Figma exports are STORE-mode ZIPs (no compression). The first 4 bytes — 50 4B 03 04 (ZIP magic) vs 66 69 67 2D 6B 69 77 69 ("fig-kiwi" magic) — determine the path. src/container.ts:loadContainer dispatches.

design.fig (ZIP STORE)
├── canvas.fig          ← real binary (fig-kiwi)
├── meta.json           ← file_name, background_color, exported_at
├── thumbnail.png       ← small preview
└── images/
    ├── <sha1-hash-1>   ← raw bytes; magic-byte sniff for type
    └── <sha1-hash-2>

The real binary lives in the ZIP entry canvas.fig. 8-byte ASCII magic + 4-byte LE version + length-prefixed chunks (typically 2 — schema, data — plus an optional thumbnail).

2.3 압축 알고리즘 자동 감지

2.3 Compression auto-detect

각 chunk 가 어떤 압축인지 표시하는 헤더는 없고, 첫 byte 로 sniff. 본 프로젝트의 핵심 발견: schema 와 data 가 다른 알고리즘. fig-kiwi npm 패키지가 단일 deflate-raw 를 가정해 modern .fig 에서 깨지는 원인.

There's no per-chunk header that tells you the algorithm — sniff the first byte. The project's core finding: schema and data use different algorithms. The fig-kiwi npm package assumes a single deflate-raw, which silently breaks modern .figs.

magic알고리즘Algorithm전형적 위치Typical chunk
28 B5 2F FDzstd (Facebook)data chunk
78 01 / 78 9C / 78 DAdeflate-zlibschema chunk (modern)
그 외otherdeflate-raw (RFC 1951)레거시 / 일부 fixturelegacy / some fixtures
function detectCompression(buf) {
  if (startsWith(buf, [0x28, 0xB5, 0x2F, 0xFD])) return 'zstd';
  if (buf[0] === 0x78) return 'deflate-zlib';
  return 'deflate-raw';
}

3. Layer 2 — Schema chunk3. Layer 2 — Schema chunk

압축을 풀면 또 binary. Kiwi 의 self-describing schema format (.bkiwi). Figma 의 schema 는 568 정의를 가짐.

Decompress and you get more binary — Kiwi's self-describing schema format (.bkiwi). Figma's schema currently holds 568 definitions.

3.1 Schema binary layout

[definitionCount : varuint]
└── for i in 0..definitionCount:
    ├── [name       : null-terminated UTF-8 string]
    ├── [kind       : 1 byte]                ─┐
    ├── [fieldCount : varuint]                │  ENUM    = 0
    └── for j in 0..fieldCount:               │  STRUCT  = 1

        ├── [type      : varint]              │
        ├── [isArray   : 1 byte (low bit)]    │
        └── [value     : varuint]             │

3.3 ENUM / STRUCT / MESSAGE — 세 wire 패턴

3.3 ENUM / STRUCT / MESSAGE — three wire patterns

Kiwi 의 진화 능력은 이 세 종류로 결정. STRUCT 는 wire 가 가장 컴팩트하지만 새 field 추가 불가. MESSAGE 는 tag-based 라 자유롭게 진화 가능 — Figma 가 schema 를 늘려도 옛 .fig 가 계속 읽히는 비결.

Kiwi's evolvability comes from these three. STRUCT is the most compact wire but can't grow new fields. MESSAGE is tag-based and free to evolve — the reason Figma can extend its schema and old .fig files still read correctly.

종류Kindwire pattern진화 가능성Evolvability
ENUM[varuint]새 value 추가 OKAdd new values freely
STRUCT[val][val][val] … (no tag)새 field 추가 ❌ — 사용중인 STRUCT 는 frozenAdding fields ❌ — STRUCTs in use are frozen
MESSAGE[tag][val][tag][val]…[0]새 field 자유 추가, optional, value 가 같으면 이름 바뀌어도 호환Add fields freely, optional, name can change as long as value stays

audit-oracle VALUE_ALIASES 는 정확히 이 진화 메커니즘의 부산물 — SPACE_EVENLY (kiwi value=3) ↔ SPACE_BETWEEN (Figma 새 명명). 같은 binary value, schema 버전 간 rename. round-trip 시 binary 보존이라 semantic 영향 0.
audit-oracle's VALUE_ALIASES is exactly a side-effect of this evolution — SPACE_EVENLY (kiwi value=3) ↔ SPACE_BETWEEN (Figma current name). Same binary value, renamed across schema versions. Round-trip preserves the binary so there's no semantic drift.

4. Layer 3 — Data chunk4. Layer 3 — Data chunk

압축을 풀면 root Message 객체 하나가 통째로. Schema 와 달리 도입부 헤더 없음 — schema 의 name === "Message" definition 을 root type 으로 약속.

Decompress and you get exactly one root Message object — no leading header. By convention, the schema definition with name === "Message" is the root type.

4.1 MESSAGE 디코딩 알고리즘

4.1 MESSAGE decode algorithm

function decodeMessage(bb, def, schema) {
  const result = {};
  while (true) {
    const tag = bb.readVarUint();
    if (tag === 0) break;                           // ★ 0 = sentinel, message end

    const field = def.fields.find(f => f.value === tag);
    if (!field) {
      skipUnknownField(bb, schema);                 // forward compat
      continue;
    }
    result[field.name] = field.isArray
      ? decodeArray(bb, field.type, schema)
      : decodeValue(bb, field.type, schema);
  }
  return result;
}

Hex sample — minimal Message

// Message { type: NODE_CHANGES, sessionID: 42 }

01                          ← tag = 1 ("type" field)
00                          ← value = 0 (enum value for NODE_CHANGES)
02                          ← tag = 2 ("sessionID" field)
2A                          ← value = 42 (varuint)
00                          ← tag = 0 → message end
                            ← total: 5 bytes

4.3 Tree reconstruction

message.nodeChanges[] 는 평탄. 메타리치 fixture 기준 35,660 entries. 트리 복원은 두 단계:

message.nodeChanges[] is flat — 35,660 entries on the metarich fixture. Two passes to rebuild the tree:

// Pass 1: index every node by GUID
const byId = new Map();
for (const n of message.nodeChanges) {
  byId.set(`${n.guid.sessionID}:${n.guid.localID}`, { ...n, children: [] });
}

// Pass 2: link children → parents
for (const n of byId.values()) {
  const pkey = n.parentIndex
    ? `${n.parentIndex.guid.sessionID}:${n.parentIndex.guid.localID}` : null;
  const parent = pkey ? byId.get(pkey) : null;
  if (parent) parent.children.push(n);
}

// Pass 3: sort siblings by parentIndex.position string (fractional indexing)
function sortChildren(n) {
  n.children.sort((a, b) => a.parentIndex.position < b.parentIndex.position ? -1 : 1);
  for (const c of n.children) sortChildren(c);
}

왜 평탄 array? Figma 의 wire format 은 streaming edits 용. 모든 변경이 NodeChange 1 개로 다중 사용자 메시지에 append. "저장된 파일" 은 그 stream 의 materialized end state 일 뿐.
Why a flat array? Figma's wire format is built for streaming edits — every change is a NodeChange appended to a multiplayer message. The "saved file" is just the materialized end state of that stream.
